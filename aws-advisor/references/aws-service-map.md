# AWS service map and practical patterns

A quick selection compass, not an exhaustive catalog. Service capabilities, names, availability, limits, and pricing change; verify the current AWS docs and What's New for the specific decision. See `aws-feature-catalog.md` for a broader domain index and `aws-service-costs.md` for regional price-pull guidance.

## Start with the workload shape

| Need | Common starting point | Choose it when | Important checks / alternatives |
|---|---|---|---|
| Event-driven code or small APIs | AWS Lambda | Work is event-triggered, bursty, and fits runtime/timeout/concurrency limits | Cold-start/latency needs, concurrency, retries, idempotency, execution duration, networking, observability, and per-request cost. Compare with containers for sustained/long-running work. |
| Containers without managing hosts | Amazon ECS with AWS Fargate | You want container packaging and managed compute, but not Kubernetes operations | Check Fargate/Region support, task sizing, startup needs, persistent storage, network/data-transfer cost, and scaling. ECS on EC2 can be cheaper at steady utilization but adds host operations. |
| Kubernetes platform | Amazon EKS | Kubernetes compatibility/ecosystem or an existing platform/team requires it | EKS adds cluster, upgrades, add-ons, security, and day-two operations. Prefer ECS/Fargate if Kubernetes is not a real requirement. Verify current EKS modes/capabilities and cost. |
| Full OS control or steady specialized compute | Amazon EC2 with Auto Scaling | You need OS/kernel/device control, special instance types, or sustained capacity | Benchmark current generations and Graviton compatibility; use autoscaling; compare Spot for fault-tolerant work and commitment discounts only after stable demand. |
| Batch jobs / workflows | AWS Batch, Step Functions, or a queue plus workers | Work is scheduled, parallelizable, or a multi-step process with retries | Model job length, checkpointing, orchestration state, retries, concurrency, and failure recovery. Verify quotas and pricing. |
| Static web content / global delivery | Amazon S3 + Amazon CloudFront (often with Route 53) | Mostly static assets need durable storage, caching, and edge delivery | Set access controls, TLS, cache rules, invalidation strategy, and WAF need. Avoid public buckets by default. |
| HTTP API ingress | Amazon API Gateway or Application Load Balancer | API Gateway fits managed API controls/serverless integrations; ALB fits HTTP routing to services | Compare auth, quotas, connection behavior, private ingress, routing needs, data processing charges, and existing compute platform. NLB is for Layer 4/TCP/UDP and network-level needs. |
| Relational SQL database | Amazon RDS or Amazon Aurora | You need SQL, relational constraints, or existing relational software | Choose engine/version/Region, storage and I/O, connections, backups, Multi-AZ, read scaling, and migration path. Aurora is not automatically cheaper or simpler; model actual workload. |
| Key-value / document data at high scale | Amazon DynamoDB | Access patterns can be expressed with keys/indexes and low-latency managed scale matters | Design keys and access patterns first; check hot-key risk, consistency, transactions, item limits, capacity mode, backups, and request cost. |
| Shared POSIX file storage | Amazon EFS or Amazon FSx | Multiple compute clients need a filesystem, or a specific enterprise/HPC filesystem is required | Choose by protocol/semantics, throughput, latency, storage class, Region, and cost. Do not use a filesystem where object storage is sufficient. |
| Object / archive data | Amazon S3 and suitable storage classes | Data is object-shaped and benefits from durable, scalable storage | Configure encryption, block public access, versioning, lifecycle/retention, replication only when justified, retrieval expectations, and request/transfer cost. |
| Cache / search / analytics | ElastiCache; OpenSearch; Athena/Glue; Redshift | You need a measured cache, search/indexing, lake queries, or a warehouse | Cache only hot data and design invalidation; search is not a primary transactional database. Choose analytics from data size, latency, concurrency, governance, and query patterns. |
| Queue / notification / event integration | SQS, SNS, EventBridge | Buffering, fan-out, pub/sub, or event routing reduces direct coupling | Design delivery as at-least-once unless docs say otherwise; make handlers idempotent, set retry/DLQ policy, and consider ordering, payload size, quotas, and event replay needs. |
| Streaming data | Kinesis or Amazon MSK | Continuous ordered/partitioned streams or Kafka compatibility is a real need | Pick partitioning/throughput, retention, consumer model, replay, ordering, and operational burden; do not use a stream for ordinary background jobs by default. |
| Identity and access | IAM roles/policies; IAM Identity Center for workforce; Cognito for app users | Different identities need scoped access with temporary credentials | Separate human, workload, and customer identity. Apply least privilege, MFA/federation, role-based access, and account guardrails. Avoid long-lived access keys and broad wildcard permissions. |
| Secrets and encryption | AWS Secrets Manager, Systems Manager Parameter Store, AWS KMS | Secrets need controlled access/rotation; encryption keys need governance | Never place secret values in source, logs, prompts, or memory files. Choose rotation/secret retrieval and KMS key policies deliberately; validate current service pricing and limits. |
| Edge protection / threat detection | AWS WAF, Shield, GuardDuty, Security Hub, Config, Inspector | Internet-facing protection, findings aggregation, configuration visibility, or vulnerability checks are required | Choose protections based on threat model and service support; validate false positives, alert ownership, logging, regional scope, and cost. |
| Metrics, logs, traces, audit | Amazon CloudWatch, AWS X-Ray / OpenTelemetry, CloudTrail | You need health/latency visibility, debugging, or an API audit trail | Define service-level indicators, alarms, log retention/redaction, trace sampling, audit retention, and ingestion cost. Do not log credentials or personal data. |
| Infrastructure as code | AWS CDK, CloudFormation, or Terraform | You need repeatable, reviewable, versioned infrastructure | Match the team's existing tool and state model. Review plans/diffs, pin versions sensibly, protect secrets, use least-privilege deployment roles, and check feature/resource support before coding. |
| ML / generative AI | Amazon Bedrock or SageMaker AI | Bedrock fits managed foundation-model/API use; SageMaker AI fits broader model development/training/inference workflows | Model/feature/Region availability changes often. Evaluate data handling, guardrails, latency, throughput, context limits, inference cost, model evaluation, and human oversight. Recheck current catalog and announcements. |

## Reusable AWS techniques

- **Account and identity foundation:** separate production from non-production appropriately; use roles and short-lived credentials; define least-privilege deployment and runtime identities; add organization-level guardrails where the team operates multiple accounts.
- **VPC layout:** use multiple Availability Zones for workloads that need resilience; keep data and application tiers private unless public ingress is required; scope security groups narrowly; consider VPC endpoints versus NAT/egress cost and controls. Validate routes and DNS without sharing exact network ranges.
- **Scale and decouple:** use load balancing and autoscaling for variable demand; queues for burst absorption and retry isolation; dead-letter handling and idempotent consumers; serverless or scale-to-zero only where cold-start, duration, and operational requirements allow.
- **Data fit:** choose from access patterns, consistency, transaction needs, size, latency, and recovery requirements—not product popularity. Plan data lifecycle, encryption, backups, restore tests, and transfer costs before launch.
- **Reliability:** set an RTO/RPO appropriate to impact. Multi-AZ is not the same as multi-Region. Choose backup/restore, pilot-light, warm-standby, or active/active only after evaluating recovery objectives, data replication, failover, and cost; test recovery.
- **Cost visibility:** tag/allocate spend, use budgets and anomaly alerts, examine service-level usage, remove idle resources, tune capacity, and include data transfer, logging, backup, support, and failure/recovery costs. Recheck the latest pricing.
- **Operations:** automate deployment/rollback, establish dashboards and actionable alarms, track quotas, use safe staged releases, and document a runbook with an owner.
- **Maturity:** use a preview feature only if its support status and lifecycle risk are acceptable. Confirm GA/preview, service/Region availability, API and IaC support, quotas, and operational implications.
